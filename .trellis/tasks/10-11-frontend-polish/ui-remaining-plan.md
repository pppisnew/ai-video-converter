### 逐项覆盖的模型（P5 实施依据）

三层语义，缺一不可：

1. **默认继承**：队列项不持有自定义参数时，读右侧面板的全局设置
   （"先调好参数再拖文件"的心智模型不丢）
2. **可覆盖**：用户改某行的格式/质量 → 该项标记为「已覆盖」，此后只读自己的参数
3. **可回退**：已覆盖项能被重置回"继承全局"

界面表现：

- 右侧面板在存在覆盖项时提示"应用到所有未单独设置的任务"
- 行的元信息按状态显示真实参数：已覆盖 `→ MKV · CRF 20`，未覆盖 `继承全局`

实现落点与风险：

- `ConvertJob`/`QueueItem` 增加 `ConversionSettings? Override`，为 null 即继承全局
- 队列执行时改用**项自身**的生效参数，而不是全局 `SettingsProvider`
- 全局面板的写回只作用于 `Override == null` 的待转换项
- 持久化（P4 的队列存储）必须一并保存该字段
- 主要风险是状态管理复杂度上升：需要在 `QueueItem` 变更时同步刷新面板提示与行内文案，并补回归测试

## 原型对比核实与计划修订（2026-10-12，第二轮）

用户拿当前实现与 `视频转换器原型.html` 做了一轮对比，转来一份"差距清单"。
**逐条核对代码后，该清单最核心的 P0 论断不成立**，已纠正，避免后续会话被同一份错误结论带偏。

### 核实：任务列表页并非"只读列表"

转来的结论称"任务列表页每个任务行只有一个 ×，失败不能重试、完成不能打开输出位置"。
实际 `src/VideoConverter/Views/QueuePage.xaml` 行内共有三个按钮，按状态显隐：

| 状态 | 行内按钮 | 原型对应 |
|---|---|---|
| 等待中 | 删除 | trash ✅ |
| 转换中 | **只有删除** | pause + close ← **唯一真缺口** |
| 已完成 | 定位输出文件 + 删除 | folder + trash ✅ |
| 失败 | 重试该任务 + 删除 | refresh + trash ✅ |

`定位输出文件` 与 `重试该任务` 分别绑定 `ViewModel.RevealOutputFor(item)` 与
`ViewModel.RetryItem(item)`，都是**按项**处理的，不是全局。
用户截图里 3 个文件全是"等待中"，所以只看到 × —— 是演示状态的错觉，不是功能缺失。

### 真正的缺口（已并入 P2）

1. **「转换中」行缺「取消」按钮**。队列严格顺序，同时只有一个 Converting 项，
   实现为 `CancelItem(item)`（item 是当前项时才调 `_queue.CancelCurrent()`）+ 行内图标按钮。
